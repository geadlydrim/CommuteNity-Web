# Codemap

Where things live and how requests flow, for finding code fast. Covers what the tree can't show: which file owns a behavior, where each glossary term lives in code, and which edits must land in several places at once. For the file list itself, look at the tree.

## Glossary term → code

Code uses the glossary's terms. The one deliberate exception is a stored JSON key (below), which changes only with a new map version.

| Glossary | Code |
|---|---|
| Post map | `map_data` on `posts`; `PostMapBuilder`, `StaticPostMap`, `PostMapPreview`, `post-map-geometry.ts`, `post-map.ts` (`parsePostMap`, `mapDataSchema`, `pinSchema`, `encodedPathSchema`, `CURRENT_POST_MAP_VERSION`). Version 2 adds `paths`: one entry per consecutive pin pair, an encoded street path or `null` (straight line); a version 1 map migrates to all-`null` paths |
| Guide | `map_data` on `comments` with `kind: "guide"`; `GuideMapBuilder`, `StaticGuideMap`, `GuidePreview`, `guide-geometry.ts`, `guide-map.ts` (`parseGuide`, `guideMapDataSchema`, `legSchema`, `CURRENT_GUIDE_VERSION`), chain rule `guideChainStatus` in `guide-chain.ts`. Version 2 legs add `vias`, `expressways`, and `path`; a version 1 leg migrates to `vias: []`, `expressways` = its mode's default, `path: null` |
| Via | `Via`, `viaSchema`, `MAX_VIAS_PER_LEG` (10) in `guide-map.ts`; stored as `vias` on a guide v2 leg, inside the Philippine pin bounds. Post maps have none |
| Leg options | `legOptions` in `src/lib/schemas/leg-options.ts`: a mode (or `POST_MAP_PAIR`) → routing profile (`walk`/`car`/`rail`) and expressways default. Also the migration's source for a v1 leg's `expressways`. The profile is derived, never stored |
| Rail file, rail slice | `src/lib/rail/rail-lines.json` (committed, ODbL: `NOTICE.md` beside it), schema `railFileSchema` in `rail-file.ts`, `prepareRail` / `sliceRail` in `slice.ts`, `loadRail` in `load.ts`. Per line (`mrt-3`, `lrt-1`, `lrt-2`): stations with stop positions, and per direction the track as one encoded polyline plus each station's metres along it |
| Transfer | `GuideTransfer`, `transferSchema`, `transferSegments`; stored under the JSON key `connectors` in guide v1 and v2 |
| Mode | `TransportMode`, `MODE_META`, `ENABLED_MODES` (walking, bus, jeepney, MRT, LRT, UV Express, P2P, tricycle) in `src/lib/schemas/modes.ts`; colour via `modeColor` in `src/lib/map/colors.ts` (a rail leg is drawn in its mode's colour, not per line) |
| Focus view | `FocusView`; `focus` prop on `PostCard`; `FocusViewDialog` (dialog shell taking children); routes `/p/[id]` and `@modal/(.)p/[id]` |
| Post vote | `post_votes` table, `net_votes` column (catalog votes are the separate `votes` table) |
| Rider | `user`, `users` table, `currentUserId` |
| Username | `username` |

## Request flow

1. `src/middleware.ts` → `updateSession` in `src/lib/supabase/middleware.ts`: refreshes the session cookie, reads the rider's `users.username` by id, and applies `gateDecision` from `src/lib/identity.ts` (no username → `/onboarding/username`; the paths allowed without one live only there). Skips static files, `/api/geocode*`, `/api/route`, and `/api/tiles/*`.
2. Pages under `src/app/` are server components that read with `createClient` from `@/lib/supabase/server`.
3. Interactive pieces are client components that write directly with `createClient` from `@/lib/supabase/client`. Reads of posts go through `@/lib/posts`; there are no server actions, and RLS in the migrations is the only authority on who can write what.

## Feature flows

**Feed** (`/`): `src/app/page.tsx` renders `SignedInHeader` + `PostComposer` for riders (viewer from `getViewer` in `src/lib/identity.ts`) and `PostFeed` for everyone. `PostFeed` (server) calls `listFeedPosts` from `@/lib/posts` (50 public posts with author, comment count, and the viewer's vote in one request) and renders a `PostCard` per post.

**Post card** (`src/components/post-card.tsx`, **server**): author, `<time>` from `formatPostTime` (`src/lib/format-time.ts`, always Asia/Manila), body, `PostMapPreview`, and an overlay link to `/p/{id}`. Interactive parts are client islands: `PostVoteControls` (instant update via `nextVote`, then adopts the server total from `setVote` in `src/lib/posts/votes.ts`; resets to fresh server props on refresh), `CommentThread` (50 comments per page via `listComments`/`addComment` in `src/lib/posts/comments.ts`, "show more", retry, chronological insert, `GuidePreview` per comment; `GuideMapBuilder` loaded with `next/dynamic` only after a signed-in rider opens it), `ShareButton` (a cancelled share does nothing).

**Focus view**: client navigation to `/p/[id]` is intercepted by `src/app/@modal/(.)p/[id]/page.tsx` → `FocusViewDialog` → `FocusView`; a direct load renders `FocusView` from `src/app/p/[id]/page.tsx`, which also emits link-preview metadata. Both fetch through `getPostById` in `@/lib/posts`. The interactive map is `FocusPostMap` in `src/components/map/`, loaded lazily via `LazyFocusPostMap`.

**Posting**: `PostComposer` inserts into `posts` (`user_id` defaults to `auth.uid()` in SQL), optionally with `map_data` from `PostMapBuilder` (loaded with `next/dynamic` on first open), then `router.refresh()`. The builder routes each consecutive pair of placed pins (`legOptions(POST_MAP_PAIR)`: car, expressways allowed) through `useRouting` (`use-routing.ts`, shared with the guide builder; one route scheduler per builder session, reset when the builder closes; `hold`/`release` bracket a pin drag) as one stretch per pair (`pairStretch` in `route-stretches.ts`, id from `pairId`): state in `routing-state.ts` (stretches keyed by an opaque id and remembering the points, profile, and expressways they were routed for; `sync` re-routes only stretches whose inputs changed, a result for a superseded token is ignored, `unavailable` stops all requests for the session; `routingWork` says which requests to start and abort), the live map draws routing pairs dimmed and dashed, failed pairs dashed and straight, routed or unavailable pairs solid. Save waits while any pair is routing, stores failed pairs as `null`, and runs `fitPostMap` (`too-large` → asks the rider to remove pins). Reopening a draft keeps its stored paths and routes only its `null` pairs. `driveRouting` (`routing-driver.ts`, no React) hands the state's work to the scheduler (below) and feeds each result back as an action; the pins move only on drag release, and a pair whose pin is being dragged makes no request until the drag ends.

**Profile** (`/u/[username]`): the page reads the rider's `users` row, then their posts with `listPostsByAuthor` from `@/lib/posts` (author attached, not re-joined); `ProfileEditDialog` renders for the owner only and replaces photos through `replaceAvatar` in `src/lib/avatars.ts` (upload → update profile → on failure delete the new upload, on success delete the old own-folder photo).

**Session resilience**: both Supabase server clients use `fetchWithTimeout` (`src/lib/supabase/with-timeout.ts`, 5 s, request really cancelled). `getViewer` throws on network/timeout errors so pages can tell "couldn't confirm" from signed out; middleware then passes the request through without touching cookies. Sign-out is a 303 that ends only this device's session. The OAuth callback redirects with relative paths; its error codes live in `src/lib/auth-callback.ts`.

**Sign-in and identity**: `public.users` is the only home of username, display name, and avatar (ADR 0006). Email sign-up checks username availability, then passes `username`/`display_name` as sign-up metadata, which only the `handle_new_user` trigger reads (it lowercases, stores NULL if invalid or taken, defaults display name from the Google name). Google sign-in lands at `src/app/auth/callback/route.ts`, then `/onboarding/username` if `users.username` is NULL. `getViewer` in `src/lib/identity.ts` is the server read of the signed-in rider. Onboarding and profile edit write only `users`.

**Geocoding**: browser → `geocode` / `reverseGeocode` in `src/lib/geo/index.ts` → `/api/geocode` or `/api/geocode/reverse` → the shared `nominatim` instance from `createNominatimClient` in `src/lib/geo/nominatim.ts` (one serialized queue ≥1 s apart across both routes, max 4 waiting → 503, 8 s budget → 504, retries, LRU cache) → `label.ts` builds place labels. Request and response shapes are Zod schemas in `src/lib/schemas/geocode.ts`, shared by routes and the browser client. Builders use it through `LocationSearch` and map clicks.

**Guide building**: `GuideMapBuilder` (`guide-map-builder.tsx`, loaded with `next/dynamic` from `comment-thread.tsx`; the draft is kept as the comment's `GuideMapData` and reopened from it) routes every road or walking leg with both ends placed as one stretch (`legStretch` / `legStretches` in `route-stretches.ts`: points = origin, the leg's vias as stored, destination; profile from `legOptions(mode)`; the leg's own `expressways`, `false` for walking; rail legs and unplaced legs are not stretches, transfers never route) through the same `useRouting`, stretch id = leg id. `sync` re-routes only a leg whose points, profile, or expressways changed, so a pin move, a via change, an expressways flip, or a mode change to another profile or default re-routes just that leg, and a mode change that keeps both (jeepney → bus) keeps the path. Vehicle legs (`hasExpresswaysChoice`) show the "Uses expressways" switch (`Switch`, `src/components/ui/switch.tsx`), preset to `legOptions(mode).expressways`; `withMode` resets it when the mode changes. Live leg lines are one GeoJSON source coloured per leg by `modeColor`, with the routing / failed styling of post maps; failed legs get a "Couldn't reshape Leg N — showing a straight line" chip, routing legs one "Routing…" chip. Save waits ("Waiting for routes…") while any leg routes, writes each leg's routed path (`null` when failed or unavailable) with its `vias` and `expressways`, and runs `fitGuide` (`too-large` → asks the author to remove legs). Reopening keeps stored paths (`seedStretchesFrom`) and retries only `null` legs; a drag of a leg's pin holds that leg's job until release. **Reshape mode**: each road or walking leg card has a Reshape button (none on rail legs, disabled until both pins are placed); `useReshape` (`use-reshape.ts`) owns the `reshape-state.ts` reducer, syncs it with the builder's legs (a removed or rail leg loses its vias), and refuses a tap or via drag outside the Philippines like a pin. The vias live in that state, not in `BuilderLeg`: the builder derives `viaLegs` (each leg with its vias) for `legStretches`, the save document and the preview, and seeds the state from the draft's `GuideLeg.vias` (`seed.legVias`). While a leg is reshaped, `handleMapClick` sends a tap to `reshape.tap` (a via in the nearest segment, never a pin); otherwise it fills the active pin. The pieces are in `reshape-panel.tsx`: `ViaMarkers` (numbered, draggable; `hold`/`release` bracket the drag so the leg routes on release), `ReshapeBanner` (stacked above the Routing… and failure chips in one overlay so none covers another), `ReshapePanel` (under the reshaped leg's card: ordered vias with ×, Undo, Clear all, Done, the 10-via note) and `StaleViasNotice` ("This leg still goes through N vias placed for the old route" with Clear vias). A pin drag or map-click placement goes through `dragPin`, a search pick through `pickPin`; both tell `reshape.pinMoved` first so the vias stay and a search pick or a drag over 1 km raises the notice. The reshaped leg's line is drawn thicker with a halo (`RESHAPE_CASING_COLOR`) unless it is routing or failed.
**Routing** (ADR 0007): a builder (`useRouting` for post maps and guides, through `createRouteScheduler` in `src/lib/routing/scheduler.ts`: jobs keyed by an opaque string (a post-map pair or a guide leg) with a `{ points, profile, expressways }` request, a 300 ms debounce per key, `hold`/`release` for drags, latest-wins aborts, a 100-result LRU cache keyed by `routeCacheKey` (profile, expressways, exact points), at most 4 requests in flight with a FIFO queue, no retry of busy or timed-out replies, and no requests once `unavailable` is seen; `reset` on builder close; `fetchRoute` in `src/lib/routing/client.ts` posts the request and parses the reply with `routeResponseSchema` / `routeErrorSchema`, `unavailable` being its own outcome) → `POST /api/route` (`src/app/api/route/route.ts`) → in order: signed-in check with the server Supabase client (401; middleware skips this route), per-rider 60/min counter in `src/lib/routing/rate-limit.ts` (429, in memory per instance), `routeRequestSchema` from `src/lib/schemas/route.ts` (2–12 points inside the Philippine bounds, `car`|`walk`, `expressways`; 400), straight-line span ≤ 500 km car / 25 km walk (400), `routerConfig()` in `src/lib/env.ts` (`ROUTER_URL` unset → 503 `unavailable`) → `requestRoute` in `src/lib/routing/valhalla.ts` (Valhalla `/route`, `auto`|`pedestrian`, vias as `through`, `use_tolls`/`use_highways`, `X-Router-Secret` header when `ROUTER_SECRET` is set, 5 s abort → 504, any other failure → 502) → `src/lib/map/path.ts` decodes the precision-6 shape, simplifies at 2 m, joins the ends to the requested points, and encodes precision 5. The answer is only `{ path, distanceKm, durationMin }`; every response is `no-store`; errors carry a `code` (`routeErrorCodeSchema`). `src/lib/map/path.ts` is the one place that encodes, decodes, simplifies, and joins paths (pure, shared with the browser). The local router is run by `scripts/router/` (`download.sh`, `build.sh`, `serve.sh`; data in `~/.cache/commutenity/router/`, see the README).

**Rail legs**: pure and browser-side, no network and never `/api/route` (`legOptions` gives MRT and LRT the `rail` profile). `loadRail()` (`src/lib/rail/load.ts`) dynamic-imports `rail-lines.json`, so the file is its own chunk that only the guide builder pulls in, and parses it with `railFileSchema`; `prepareRail` decodes each track once. `sliceRail(rail, mode, start, end)` (`slice.ts`) snaps each pin to the nearest station of the mode within `RAIL_SNAP_RADIUS_METERS` (250 m, by distance to any of the station's stop positions), picks among lines serving both pins (smallest total snap distance; LRT-1 / LRT-2 at Doroteo Jose / Recto), takes the direction in which the first station comes before the second, cuts the track between the two stations' positions, and `joinEnds` attaches the pins. A failure returns `{ ok: false, reason }` with `no-station`, `same-station`, or `different-lines`, which the builder maps to its straight line and mode-specific hint. The file comes from `scripts/rail/build-rail.sh` (`build_rail.py`, pyosmium in a venv under `~/.cache/commutenity/rail/`) over the router's extract, relations picked by ID and checked against their `route_master`; `tests/support/rail-fixture.json` is a few stations per line cut from it.

**Rail legs in the builder**: `useRail(needed)` (`use-rail.ts`) calls `loadRail()` only once the guide has a rail leg (never for the feed, never for a guide without one) and reports `idle` / `loading` / `ready` / `failed`. `railLegOutcomes` (`rail-legs.ts`, pure) turns each rail leg with both ends placed into `{ ok: true, points, path }` (`sliceRail` plus `encodePath`) or `{ ok: false, hint }`, with mode-specific copy from `railHint` ("Not near an LRT station — move the pin to a station to follow the line", and the same-station, different-lines, and load-failed variants). The builder saves `path` for a sliced leg and `null` otherwise, draws the slice solid (a leg with no slice is a straight line shown with its hint in the leg card, a leg waiting for the file is dimmed and dashed), and Save waits ("Waiting for routes…") only while the rail file is loading. A rail leg has no Reshape button and no expressways switch, and `buildGuide` writes `vias: []` for it. Thumbnails and the focus view draw the stored path like any other leg path.

**Maps**: `@/components/map` is a server-safe barrel (static previews only). Feed thumbnails are `<img>` tiles + SVG drawn by `StaticTileCanvas` (`static-*-map.tsx` are thin mappers onto it). Every tile URL comes from `src/lib/map/tiles.ts` and is served by the caching, Philippines-only proxy `src/app/api/tiles/[z]/[x]/[y]/route.ts`. Live MapLibre (`MapView`) mounts only in the focus view and the two builders, loaded with `next/dynamic`; `react-map-gl` is re-exported only by `src/components/map/primitives.ts` for use inside the folder. Reading stored maps: `parsePostMap` / `parseGuide` (unknown newer versions show a placeholder). Stored paths: the thumbnail and `FocusPostMap` take the parsed `MapData`; the pure helpers in `post-map-geometry.ts` decode each pair's path (`decodePath`) into the drawn line (`postMapLinePoints`; a `null` or undecodable pair is the straight line between its pins) and frame the view on pins plus every path point (`postMapFramingPoints`, `fitPostMapToView` over the generic `fitPointsToView`, which guides reuse). The server-rendered thumbnail imports only the pure `path.ts`, so the feed bundle stays free of MapLibre. Guides draw the same way: `guide-geometry.ts` gives each leg its stored path (`legLinePoints`, via `storedPathPoints`; `null` or undecodable is the straight line between its ends), `legSegments` colours it by mode, transfers stay straight dashed segments, and `guideMapFit` frames pins plus every leg's path points (`guideFramingPoints`). `StaticGuideMap` is the only place a guide is drawn outside the builder: the focus view shows a guide through the comment thread's `GuidePreview`, so there is no live guide map.

## Edits that must land in several places

- **Post reads**: one selection in `src/lib/posts/select.ts`, the UI type `Post` in `src/lib/posts/types.ts` (normalized by `toPost`), reads in `src/lib/posts/queries.ts`. A new column is a `select.ts` + `types.ts` change; regenerate row types first if it's a new database column.
- **Map editing**: both builders run on one core: pure slot transitions, per-slot request tokens, and the Philippines bounds check in `src/components/map/map-editor-state.ts`; the `useMapEditor` hook (`use-map-editor.ts`) for active slot, picking, placement, reverse-geocode aborts, fly-to, and fitting the first camera to the seeded pins (or the `framingPoints` a builder passes, e.g. a draft's stored paths); shared `BuilderShell` and `SlotFields`. A placement or labeling fix goes there, not in a builder. Street-path routing state is a separate pure module per builder shape, not part of the slot state: `routing-state.ts` for both builders' stretches (post-map pin pairs, guide legs; see Posting and Guide building), with `route-stretches.ts` turning each builder's shape into stretches; `reshape-state.ts` for guide legs' Reshape mode (one reshaped leg, per-leg vias capped at `MAX_VIAS_PER_LEG`, nearest-segment insertion via `nearestInsertIndex`, via-only undo, the big-move "old route" notice, `legPoints` for the routed point sequence; rail legs can't be reshaped).
- **Routing limits**: 2–12 points, the 500 km / 25 km spans, and the response shape live in `src/lib/schemas/route.ts`; the 60/min and 5 s limits in `src/lib/routing/` (`ROUTE_LIMIT`, `ROUTER_TIMEOUT_MS`); the 2 m simplification in the route handler. Philippine bounds are `PH_LAT_RANGE`/`PH_LNG_RANGE` from `post-map.ts`, reused by the route schema. Changing the profile or option mapping touches `valhallaRequestBody` in `src/lib/routing/valhalla.ts`.
- **Rail file**: the line list (relation IDs, route_master IDs) lives in `LINES` in `scripts/rail/build_rail.py`; the file's shape in `src/lib/rail/rail-file.ts` (change both, then rebuild with `scripts/rail/build-rail.sh` and refresh `tests/support/rail-fixture.json` from the new file if stations moved). The 250 m snap radius is `RAIL_SNAP_RADIUS_METERS` in `slice.ts`.
- **Colours**: one source, `src/lib/map/colors.ts` (pin roles, post-map line, `modeColor`, the reshaped leg's halo), used by thumbnails, live maps, and builders.
- **Username rules**: the regex lives in `src/lib/schemas/profile.ts` and the `users_username_format` CHECK, and `handle_new_user` re-checks it at sign-up.
- **Database error messages**: one mapper, `riderMessage` in `src/lib/errors.ts`, used by every form and write; add new error cases there, keyed on codes and the database's named exceptions (`username_cooldown`, `avatar_url_invalid`), never on loose message text. A new named exception raised in SQL needs a case there.
- **Limits shared with SQL**: post/comment body 500 and non-blank (`src/lib/schemas/post.ts` ↔ CHECKs), `map_data` ≤ 16 KB of jsonb (CHECKs in `content_limits`) ↔ `MAP_DATA_BUDGET_BYTES`, 12 KB of UTF-8 JSON, in `src/lib/map/fit-document.ts` (jsonb stores coordinates larger than their JSON text, up to about 3 KB more for a maximal guide, hence the headroom; `fitPostMap` / `fitGuide` re-simplify the longest paths at 5, 10, then 20 m before a save and report `too-large` past that; `tests/db/content-limits.test.ts` checks the budget against the real CHECK with maximal documents), Philippine pin bounds (`post-map.ts` ↔ reverse-geocode schema in `geocode.ts`), avatar types and 5 MiB (`src/lib/avatars.ts` ↔ bucket settings in `20261022000000_rider_write_guards.sql`), display name ≤ 40 (`profile.ts` ↔ `profile_limits`).
- **Row types**: generated in `src/lib/supabase/database.types.ts` by `npm run db:types`; regenerate in the same change as any migration.

## Tests

`npm test` runs Vitest over `tests/**/*.test.ts` in Node.

- `tests/db/`: act as a rider against the database in `SUPABASE_DB_URL` (the linked, live project) inside transactions that always roll back; `tests/db/rider.ts` is the harness (`withRollback`, `createRider`, `actAs`, `run`). `DB_TEST_MIGRATION=<file.sql>` applies an unpushed migration inside each test first, so a new migration can go red → green before `supabase db push`. These suites skip when `SUPABASE_DB_URL` is unset.
- Concurrency tests need real commits: `withCommittedFixtures` in the same harness opens separate sessions and always deletes the riders it created (cascading to their posts and votes). `DB_TEST_MIGRATION` can't apply to these, so they go red before the push and green after.
- `tests/unit/`: pure modules in Node (e.g. the error mapper, the path codec in `path.test.ts`, the route scheduler with a fake clock and fake fetch in `routing-scheduler.test.ts`, the routing state for post-map pairs in `routing-state.test.ts` and for guide legs in `route-stretches.test.ts`, rail slicing in `rail-slice.test.ts` against the small real-data fixture in `tests/support/rail-fixture.json` and the committed rail file, rail legs (path or hint, hint copy) in `rail-legs.test.ts`).
- `tests/api/`: call route handlers directly with a `NextRequest` and spy on `fetch`; the routing test also stubs the session (`@/lib/supabase/server`) and the router environment.
- No component tests; client components have no injection seam yet.
